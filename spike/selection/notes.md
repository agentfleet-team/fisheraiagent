## 5. Findings for RFC-3 (written by the builder)

Cloud workflow runs (artifact `spike/selection/results/`): https://github.com/agentfleet-team/fisheraiagent/actions/runs/45875754119 (pull_request run + re-run; only attempt 2's artifact survives — `gh run rerun` deletes the earlier attempt's artifacts — so `gha-4-2.json`), https://github.com/agentfleet-team/fisheraiagent/actions/runs/45876169421 (`workflow_dispatch`, `gha-5-1.json`), and https://github.com/agentfleet-team/fisheraiagent/actions/runs/45876486482 (pull_request run on the exact PR head, `gha-6-1.json`). Same result all three times.

- **Filters bound the window:** across both Mac runs, every week-filter entry that carried age text was <=8 days old and every month-filter entry <=32 days (0 outliers). The upload-date filter is the freshness gate; rank-1 hits are now minutes-to-days old, where the round-1 relevance-sorted search surfaced 46-597-day-old videos at the top.
- **Keyless search from the cloud:** 54/54 yt-dlp search calls on `ubuntu-latest` succeeded across 3 runs, and 54/54 page reads succeeded too — the same direct `fetch` that gets bot-walled on the per-video endpoint is not walled on the search page. On the Mac: 36/36 searches, 35/36 page reads (one transient `no ytInitialData in page` on an HTTP-200 body). But 0/81 cloud video calls succeeded: every `-J --skip-download` returned `Sign in to confirm you’re not a bot` (exact text in section 4).
- **Fields without a second call:** at `--playlist-end 20`, flat entries carry `id`, `title`, `duration` every time; the page read adds the relative age text (604/720 Mac, 906/1080 GHA entries) and the CC badge (158/720 Mac, 229/1080 GHA). A quality bar can gate on duration, age and CC presence with no per-video call. `channel`/`view_count` were absent from yt-dlp's flat entries on 4/36 Mac searches and 7/54 GHA searches — an A/B layout gap on YouTube's side (the round-1 verdict's side finding), not a block; the values exist in the page's `ownerText`/`viewCountText` but this spike only recorded the yt-dlp-side count.
- **Two fetches, two tails:** the yt-dlp fetch and the page fetch of the same URL disagreed on ~3.5 of 20 ids per search (63 ids each way on mac-1). YouTube rotates tail results between identical keyless requests; entries without `age_text` are mostly these mismatches, not parse failures.
- **Cost of the second call:** ~1.0 s median per search call, ~0.4 s per page read, ~1.3 s per full-metadata call on the Mac. The nightly set (9 queries x 2 filters) costs ~20 s of searches + ~36 s for the top-3 probes.
- **`ytsearchdate` is gone:** the ticket named `ytsearchdate20:`; `YoutubeSearchDateIE` no longer exists in yt-dlp 2026.11.23 (`Unsupported url scheme`). The `/results` URL with an `sp` parameter is the same flat-playlist path.
- **Nightly supply (deduped per place — 2 Mac runs, 3 GHA runs — 8-90 min band, page fields only):** <=7 days — 38-47 unique videos per topic on the Mac, 44-54 on GHA; <=30 days — 39-47 Mac, 45-54 GHA. Against round-1's relevance-sorted 0-1/topic (<=7d) and 1-3/topic (<=30d), the corrected search shows the nightly supply is ample, not marginal.
- **Caption presence (Mac, 54 probed):** `zh*` on 49/54, `en` on 47/54, neither on 5/54 (nearly all via `automatic_captions`). The page CC badge is a coarser signal — it marks closed captions exist but not the language; zh/en presence still needs the per-video call, which is bot-walled in the cloud.

RFC-2 note: the split moved. Round 1 said candidate generation works in the cloud but the quality bar does not. Round 2 shows the whole page-fields quality bar — freshness window (search filter), relative age, duration, CC presence — works keyless on `ubuntu-latest`. Only the fields that need the per-video endpoint (exact `upload_date`, `channel_follower_count`, zh/en caption languages) stay bot-walled in the cloud; if the quality bar accepts page fields only, all of selection can run in the cloud.
